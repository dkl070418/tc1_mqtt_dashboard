## 2. 两代固件的协议对照

| 维度 | 原厂固件 v1.x（闭源，我们的 v1） | zTC1 v2.5.x+（开源，我们的 v2） |
|---|---|---|
| 控制命令 topic | `device/ztc1/<mac>/set`（每设备独立） | `device/ztc1/set`（全体共享） |
| 命令形态 | JSON：`{"mac":..,"plug_N":{"on":1}}`、`{"mac":..,"plug_N":{"setting":{..}}}` | 文本：`set socket <大写MAC> <idx> <on>`、`set total_socket`、`set childLock`、`reboot <MAC>` |
| 状态上报 | `device/ztc1/<mac>/state`（JSON，含 `plug_N.on` 与 `setting.task_K`） | `device/ztc1/<MAC大写>/state` + `homeassistant/...` discovery |
| 任务配置入口 | **MQTT**：`{"mac":..,"plug_N":{"setting":{"task_K":{hour,minute,repeat,action,on}}}}` | **HTTP** `/task`（GET/POST/DELETE）；MQTT 无任务命令 |
| 任务槽位 | 每插口 5 个：`task_0`…`task_4`（`task_4` 被本项目用作"倒计时/任务5"） | `MAX_TASK_NUM` 个链表节点，`GetTaskStr()` 输出 `id/timestamp/prs_time/operation/on/weekday` |
| 重复语义 | `repeat` 位掩码：`bit0=周一 … bit6=周日`，`0`=一次性，`127`=每天 | `weekday` 枚举：`0`=一次性、`8`=每天、`9`=工作日、`10`=周末、`1`–`7`=周一…周日 |
| 动作语义 | `action`：`0`=关、`1`=开（原厂 App `String[] action={"关闭","开启"}` 直接取索引） | `operation`：`SWITCH_SOCKET_1..6` / `SWITCH_ALL_SOCKETS` / LED / 儿童锁 / 重启 / 恢复出厂 |
| 一次性任务执行后 | **实测**：该 `task_K` 从 `setting` 里消失（22:44 实测） | **源码**：`DelFirstTask_nolock()` 里 `weekday==0` → `on_use=false`，槽位释放（`timed_task.c:165-169`） |
| 周期任务执行后 | **实测**：任务保留 | **源码**：`weekday==8` → `prs_time += 86400` 重新入链；`1-7` → `+= 7*86400` |

> 两代固件都**没有**"MQTT 设置时间"的官方命令。原厂 App 全仓无 `time` 载荷；
> zTC1 v1.1.0 的 `setting` 解析只认 `ota/name/mqtt_uri/mqtt_port/mqtt_user/mqtt_password`
> （`mqtt_server/user_function.c`），**完全没有 `time` 字段**。zTC1 v2.5.x 也只有 `user_rtc.c` 自己 SNTP。

## 3. 时间从哪来（这是"任务延期/不执行"的根源）

### 3.1 zTC1（v2，有源码，确定）

`TC1/time_server/user_rtc.c`：

- **SNTP 校时**，服务器列表（`:24-30`）：`pool.ntp.org`、`cn.ntp.org.cn`、`cn.pool.ntp.org`、
  `s1a.time.edu.cn`、`ntp.sjtu.edu.cn`；另有一个硬编码 IP `0xd248912c`（= **44.145.72.210**）先试。
- **校时时机**（`:127`）：`rtc_init != 1 || (tm_sec == 0 && tm_min == 0)`
  → **开机（连上 WiFi 后）+ 每小时整点各校一次**。
- **时区**（`:106`）：`utc_time += 28800`，即固件内部按 **UTC+8** 比较任务时刻。
- **SNTP 失败时**：`rtc_init = 2` → 每 900ms 循环重试；芯片 RTC 不自带电池，
  **断电/重启后若一直连不上 NTP，时钟没有任何可信来源**（`MicoRtcSetTime` 已注释掉，`:124`）。

→ 结论：**v2 设备的时间完全取决于能否访问 NTP**。NTP 不通 = 任务永不触发或错时触发。

### 3.2 原厂 v1（闭源，实测+推测）

- 原厂 Android App **从不给设备推时间**（`SmartControl_Android_MQTT` 全仓只有 M1 设备有 `"time":-1`），
  反推：原厂固件自己也必须有一条走时/校时路径 —— **推测同样是 SNTP**（同平台 MiCO 有 `sntp` 库），
  但没有源码，无法证实。
- 设备 `state` 里**没有任何时钟字段**，`setting.{...}` 也不回显时间 → **无法回读设备时钟**。
- 本项目 v1.4.12 加的"同步设备时间"发的是 `{"mac":..,"setting":{"time":<unix秒>}}`，
  **该字段不在原厂协议里**（原厂 App 无此载荷）。当年注释的"设备回 `setting:{}` 确认"
  只是固件对任意 setting 写入的通用回显，**不能证明校时成功**。
- **实测旁证**：`a1b2c3d4e5f6` 运行时长（`sensor.total_time`）**215 天 15 小时**未重启；
  按普通晶振 ±20~50 ppm、若长期未校准，累计漂移约 **6~16 分钟** —— 与"定时任务定期延后"的量级吻合。

### 3.3 对照实现：zTC1 v1.1.0 的任务引擎（源码，`zogodo/zTC1` tag `v1.1.0`）

这一段是**同硬件平台上另一份实现**，用来推断原厂固件的行为边界（不是我们设备在跑的代码）：

`TC1/time_server/user_rtc.c` 的 `rtc_thread()` 里既有 SNTP，也有整个任务引擎（`while(1)` + 900ms 睡）：

```c
mico_time_get_utc_time(&utc_time);
utc_time += 28800;                        // 固定 +8 区
struct tm * currentTime = localtime((const time_t *) &utc_time);
...
for (i = 0; i < SOCKET_NUM; i++)
  for (j = 0; j < SOCKET_TIME_TASK_NUM; j++)
    if (user_config->socket[i].task[j].on != 0) {
        char repeat = user_config->socket[i].task[j].repeat;
        if ( rtc_time.sec == 0                                   // ← 只认"整分 0 秒"
          && rtc_time.min == user_config->socket[i].task[j].minute
          && rtc_time.hr  == user_config->socket[i].task[j].hour
          && ((repeat == 0x00) || repeat & (1 << (rtc_time.weekday - 1))) )  // ← 见下方星期 bug
        {
            if (user_config->socket[i].on != user_config->socket[i].task[j].action) {
                UserRelaySet(i, ...action);
                user_mqtt_send_socket_state(i);
            }
            if (repeat == 0x00) {                                 // ← 一次性任务执行后自动停用
                user_config->socket[i].task[j].on = 0;
            }
        }
    }
```

从中能读出四条**对排障极关键**的事实：

1. **触发窗口只有"整分第 0 秒"**，而主循环是 `mico_rtos_thread_msleep(900)` 轮询。
   900ms 轮询必然偶尔跨过 `sec==0` 那一瞬（约每 10 次漏 1 次）→ **任务会偶发整分钟被跳过**。
   这是"任务时好时坏"的结构性原因，不是网络问题。
2. **一次性任务执行后固件自己把 `on` 置 0**（不是删行）→ 与本项目 v2.1.0 注释里"固件执行后不停用"的说法相反，
   与我们在原厂 v1.3.0 上观察到的"任务消失"一致。
3. **星期位有 bug**：`1 << (rtc_time.weekday - 1)`，而 `tm_wday` 是 **0=周日**。
   周一(1)→bit0 ✓、周二(2)→bit1 ✓ … 周六(6)→bit5 ✓，但**周日(0)→`1 << -1`，是未定义行为**。
   即：**周一~周六的"周几"设置有效，周日的设置不可靠**（`repeat=127` 在周一~周六正常，周日看编译器脸色）。
4. SNTP 与任务判定在**同一个线程**里串行执行；`sntp_get_time()` 是阻塞的（要试 6 个服务器）。
   网络差时这一步会拖住线程 → 更可能错过 `sec==0` 窗口。

> 原厂 v1.3.0 是闭源，不能断言它也是这样实现；但真机上观察到的两个现象
> （一次性任务执行后消失、触发时刻比设定分钟晚约 60 秒）与这套逻辑完全吻合。

## 4. 本项目介入的两条路径

| | v1 设备（原厂固件） | v2 设备（zTC1） |
|---|---|---|
| 定时任务由谁执行 | **排插自己**（固件内部定时器） | **我们的后端**（`backend/scheduler.go`，15s tick） |
| 依赖设备时钟？ | **是**（hour:minute 与设备本地时间比对） | **否**（用服务器时间；设备时钟无关） |
| 错过补发 | 无 | `scheduler_catchup_minutes`（默认 30 分钟，日志标"已补发"） |
| 时间同步 | 前端 4 个事件点 + `v2.1.5` 后端每 6 小时推 `setting.time`（有效性见 §3.2，**未证实**） | 不需要（除了固件自身 SNTP） |

前端推时间的 4 个事件点（`App.vue` / `DeviceControl.vue`）：
① 打开控制台并连上 MQTT 后设备首条 state 到达；② 设备离线转在线；③ 手点"同步设备时间"；④ 保存倒计时前。

## 5. 真机实验记录（设备 a1b2c3d4e5f6，只动 plug_0=插口1）

| 时间 | 实验 | 结果 |
|---|---|---|
| 22:22 | 推 `setting.time` = now+300 秒，再写 `task_4`=22:29 | 任务被接受并回显；观察窗内未动作（窗口太短 + 清理过早，**不作结论**） |
| 22:26 | 推 `setting.time` = now−600 秒，写 `task_4`=22:17 | 未动作（若时钟被推慢 10 分钟，该时刻在设备看来已过去 —— 设计所致） |
| 22:35 | 整插口写全 5 个任务，`task_4`=22:38 | 任务在 22:37:40 左右从 `setting` 消失，插口未动作（`action=0`，插口本就是开） |
| **22:43** | 推正确时间 → 关灯 → 写 `task_0`=22:43 `action=1` | ✅ **灯在 22:44:05~22:44:15 亮起**，任务随后被固件清空（一次性任务自清除） |
| 00:15 / 00:21 / 00:23 / 00:33 / 00:40 | 循环 `repeat=127` + 一次性对照，多个窗口 | ❌ 全部未动作；循环任务保留在设备上，一次性任务也保留（与 22:43 不同） |
| 00:37 | 复刻原厂 App 的"查询包"再写任务 | ❌ 未动作（排除"需要先查询才装载"） |
| 00:53→01:25 | **不推任何时间**，写 `repeat=127` = 01:03，30 分钟窗口每 30s 采样 | ❌ 完整窗口（00:53:25→01:25:06）内从未动作；任务始终 `on=1` 保留。收尾已把灯恢复 ON、任务清空 |

**归纳**：8 组实验里 7 组失败、1 组成成功（22:43）。失败与是否推过时间、写入形状、是否先查询都无关；
唯一稳定现象是"任务被接受并保留，但不触发"。这与 §3.3 的"只在整分 0 秒判定 + 900ms 轮询"高度吻合 ——
**只要设备时钟与真实时间差 ≥1 分钟，我们按真实时间设的任务在它看来就永远对不上**。

### 5.1 关于 `repeat=127` 是否有效

**机制层面有效**：原厂 App 与其 UI 完全一致（`TC1PlugActivity.java:345`），位序 `bit0=周一`（`Function.java:73-89`），
`0`=一次、`0x7F`=每天；设备 `state` 里确实长期保存着多条 `repeat` 任务（如 plug_5 的 9/108/3/96）。
**但真机上多次未触发**，且最后一轮连"一次性对照"也未触发 → 当前现象是**设备侧时间/调度状态**问题，
不是星期位或 payload 格式问题。

## 6. 已确定 vs 待验证

**已确定（源码/协议/实测）**

1. 三台设备的固件归属：两台原厂 v1.x（闭源）、一台 zTC1 v2.5.2+（开源）。
2. 原厂协议的任务写入格式、5 槽位、`repeat` 位掩码、`action` 语义、一次性任务执行后自清除。
3. 原厂固件的 `setting` 解析里**没有 `time`**（zTC1 v1.1.0 源码旁证：只认 ota/name/mqtt_uri/
   mqtt_port/mqtt_user/mqtt_password）→ 本项目 v1.4.12 起的"同步设备时间"**对 v1 设备无效**。
4. zTC1 的时间来自 SNTP（开机 + 每小时整点），时区 +8，NTP 不可达则无可信时间。
5. zTC1 的任务只能经 HTTP `/task` 配置，MQTT 无任务命令（这正是本项目给 v2 写后端调度器的原因）。
6. zTC1 任务引擎的判定窗口只有"整分第 0 秒"，主循环 900ms 轮询 → 结构性会漏触发。
7. 一次性任务执行后固件把 `on` 置 0（zTC1 源码）；原厂实测任务从 `setting` 消失。
8. 设备的 `sensor.total_time` 可用于读运行时长（判断是否重启过）。

**待验证**

1. 原厂 v1.3.0 的采样/判定细节（无源码，只能靠行为推断；已排除"payload 形状不对"）。
2. `setting.time` 在原厂固件上确认无效这一条，目前是"旁证 + 行为不符"，缺一个正面实验
   （要在设备时钟与真实时间差 ≥1 分钟时验证，需要先能量出偏差）。
3. 原厂固件的星期位是否也有 zTC1 那样的"周日越界"问题（未验证；本项目 `repeat=127` 在周一~周六正常这一点两台固件一致）。
4. 原厂固件停电重启后时钟的起始值（是否会回到 1970；这会决定"断电重启"能否作为修复手段）。

## 8. 结论与建议

1. **v1 设备的定时任务原生依赖排插自己的时钟**，而它的时间只能靠固件自己（同平台对照实现用 SNTP）获取。
   我们项目的 `setting.time` **在原厂固件里根本没有对应解析分支**（zTC1 v1.1.0 源码旁证 + 真机行为不符），
   属于"发出去没人接"的字段 —— 它能让日志显示"成功 2"，但**不改变设备时钟**。
2. 因此"v1 定时任务延期/不执行"**不是本项目的 bug**，而是这一代固件的固有短板。已确认的机制：
   - 判定窗口只有**整分第 0 秒**，且主循环 900ms 轮询 → 结构性漏触发；
   - 时间靠固件自身 SNTP，NTP 不通就没有可信时间（同平台实现里 SNTP 与任务判定还在同一线程串行）；
   - 一次性任务执行后自动停用（`on=0`），所以"配了一次性任务只跑一次就没了"是**设计行为，不是 bug**。
3. 朋友们反馈的"延期一分钟左右"对得上第 1 条；"十几分钟量级"对得上时钟漂移（本机这台 215 天未重启，
   按 ±20~50 ppm 估算漂移 6~16 分钟）。
4. **根治方案（v2.1.6 已实现并实测）**：把 v1 也纳入后端调度（与 v2 同一套 `scheduler`，用服务器时间到点
   直接发开关命令），彻底绕开设备时钟；开关 `v1_backend_scheduling`（默认关），实现与实测见 §9。
5. 短期建议：把 `setting.time` 的定位从"校时功能"降级为"对 v2 无用、对 v1 无效"的遗留开关
   （保留但默认关闭，或在界面上注明"该功能对本代固件无效"），避免下次有人拿日志"成功"当生效证据。

## 9. 附录：v1 纳入后端调度（**v2.1.6 已实现并实测通过**）

> 实现位置：`backend/scheduler.go`（`loadScheduledTasks` 按固件分流 + `adoptV1Tasks` 接管）
> 开关：`v1_backend_scheduling`（默认 `false`，总闸）
> 粒度：**每个任务**用自己的 `exec` 字段决定归属（`v2.1.7` 起）
>   - `exec: "server"` + 总闸打开 → 后端按服务器时间执行；设备侧同名槽位写 `on:0`
>   - 缺省 / `exec: "device"` → 排插自己执行，**后端既不调度也不改动**（安卓 App 建的任务就是这个形态）
> 实测：2026-11-24 03:23~03:27，生产设备 `a1b2c3d4e5f6`，A/B/C/D 四个场景全通过（详见 CHANGELOG v2.1.7）

目标：让 v1 设备的定时任务**不再依赖排插时钟**，与 v2 共用一套后端调度语义。

```
backend/scheduler.go
  loadScheduledTasks()             // 按固件分流
    ├─ v2: publish "set socket <大写MAC> <idx> <on>"      → device/ztc1/set
    └─ v1: publish {"mac":..,"plug_N":{"on":0|1}}          → device/ztc1/<mac>/set
  adoptV1Tasks()                   // 把设备侧同名任务写 on:0（每分钟复查），防双触发
  tick()                           // 15s 一次，用服务器 CST 时间判定
  scheduler_fires 表               // 去重键：(mac, plug, task, fire_minute)
```

要点：

1. **不需要设备时钟**：判定用服务器时间；下发的是"开关动作"而不是"任务配置"。
2. **去重与补发**：沿用现有 `scheduler_fires` + `scheduler_catchup_minutes`，v1/v2 行为一致。
3. **与设备侧任务的关系**：若设备里仍留着同样的 `task_K`（on:1），会出现**双触发**（固件 + 后端）。
   需要一个开关：启用后端调度时，把设备侧对应任务写 `on:0`（或在界面上明确"由服务器执行，设备任务已停用"）。
4. **离线降级**：设备离线时后端仍会"触发"（发布命令），但在线后补发窗口内会重发；
   超出窗口则记为错过（与 v2 相同）。
5. **配置项**：`v1_backend_scheduling: true|false`（默认 false，灰度开启），
   `v1_time_sync_interval_hours` 保留但降级为辅助。
6. **风险**：一次双触发可能误关设备（如插口2断电），因此开启时应先在单台设备、单个插口上验证，
   并保留"一行配置回滚"。

### 与现状对比

| 方案 | 依赖设备时钟 | 断网/离线 | 改动量 | 风险 |
|---|---|---|---|---|
| 现状：固件执行 + 6h 推时间 | 是（且推送有效性未证实） | 离线仍执行（固件自己跑） | 已完成 | 低 |
| **v2.1.6：后端调度 v1（已实现）** | **否**（服务器时间） | 离线不执行，窗口内补发 | 已完成并实测 | 双触发已由 `adoptV1Tasks` 堵住；灰度开关默认关 |
| 后端调度 v1 | 否 | 离线不执行，窗口内补发 | 中（复用 v2 调度器） | 双触发/误断电，需灰度 |
| 混合：默认固件执行，界面提供"改由服务器执行" | 否（切换后） | 同上 | 中+前端改动 | 低（用户显式切换） |
